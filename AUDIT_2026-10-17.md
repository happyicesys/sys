## Recurring patterns (what to change in how features get built)

1. **Each new write route gets its own permission middleware**, per verb (`->only([...])`), as `StockCheckController` and `ServiceNoticeController` already do. Three findings this window came from older routes that new, heavier features were added to: apk-settings, product mappings and batch attachments.
2. **Every state transition that moves money or stock opens with an atomic claim.** For example: `UPDATE … WHERE status = X`, or `lockForUpdate` plus a re-check, inside `DB::transaction`, with side effects queued `afterCommit`. The codebase already does this well in `FreezerRecognitionService::submit` and `ProductWelcomeSketchService::generate`. The ops-job, stock-check, settlement-sync and stock-adjust paths do not.
3. **A queued job never carries an absolute qty taken at dispatch time.** Either it reads at run time, or it is seed-only (`qty_seed_only`).
4. **No supplier HTTP call or ffmpeg run inside a web request** unless the user must have the answer right now. Even then, use a short request-scoped timeout and at most one retry.
5. **Every append-only log or slot table gets a prune command when it is created**: `card_payment_events`, `happy_hour_slots`, `ota-cache`.
6. **A rule written twice becomes one class.** The repo already proves this works: `DispenseVerdict`, `OperatorScope::DEFAULT_FILTER_CODES` and `NoInline*Test` guards. Use the same approach for the HH sale rule, TRADE-frame parsing, freezer product ids and money formatting.
7. **Vue:** a feature added to a page over 1,500 lines arrives as a component plus a composable, not as more refs in the page's `<script setup>`.

### CARD-01 — The NETS refund reconciler judges T05 (Payrallel) card sales as "not captured by NETS"
**Status:** FIXED f2c6cf94d1 — reconciler counts only bindings whose unit `settlementProvider()` is `nets`; T05 sales read `unbound`. Prod repair after deploy (Brian): `php artisan card-settlement:reconcile-refunds --from=2026-10-05 --to=2026-10-09` (dry run), then `--apply`. Txn/Revenue reads T05 revenue from `card_payment_intents.captured_cents`: see the follow-up commit on the same branch.
**Sev** High · **Lens** Correctness / money · **Verdict** CONFIRMED (prod data) · **Effort** S
**Where** `app/Services/CardSettlement/CardSettlementRefundReconciler.php:189-193` (classify), `:476-491`, `:545-563` (`terminalsByVend`), `:376-400` (`applyNotCaptured`)

**What**
- Since 2026-10-03 a T05 is a `card_terminal_units` row bound through `card_terminal_bindings`. Freezer T05 sales are written with payment method code 1 (Card Terminal).
- `salesOn()` takes every Card Terminal sale. `terminalsByVend()` treats any binding as "bound", and Payrallel is not in `report_coverage_gap_companies`, so the sale counts as "covered". On a NETS-final day with no NETS line, the state is `not_captured`.
- The matcher has a provider guard (`restrictToProvider`). The reconciler has none.
- Consequences:
  - A failed single-item T05 sale gets `is_refunded = 1` with source `settlement_report_not_captured` ("NA in NETS"), and `crossTickets` pulls its refund ticket out of payout, even when Payrallel captured money (AI verdict or the 72 h backstop).
  - Dispensed T05 sales read `not_found` on Txn, Revenue & Settlement, show the badge "No line in NETS", and count in the health email's "dispensed but not charged" figure.

**Evidence** (prod, vend 50001 since 2026-10-03):
```

bindings: 50001 → N620W325842 / N620W342856, company "Payrallel (T05)"
```
```php
$unit = $terminals->get((int) $sale->vend_id);
$state = $this->classify($line, $final, $unit !== null, $unit ? ! $unit->hasReportCoverageGap() : false);
```

**Fix**
- In `terminalsByVend`, or before `classify`, skip a unit whose `settlementProvider() !== 'nets'`, or give it a new state such as `other_rail`. Exclude it from `unexplainedNoLine`.
- Make `TxnRevenueSettlement` read T05 revenue from `card_payment_intents.captured_cents`.
- Clear the 13 stale states on prod.

**Verify** Add a feature test: a freezer sale with a T05 binding and a final NETS day keeps a NULL state and no tick. Then on prod: `SELECT COUNT(*) FROM vend_transactions t JOIN card_terminal_bindings b … company='Payrallel (T05)' WHERE card_settlement_state IS NOT NULL` returns 0.

### CARD-02 — Auto-capture (and the non-AI device capture) resends a capture whose outcome is unknown
**Status:** FIXED f2c6cf94d1 — new intent state `capturing` (write-ahead); uncertain captures are flagged, never resent; `card-payments:resolve-charge` covers both paths.
**Sev** High · **Lens** Money / idempotency · **Verdict** CONFIRMED (code) · **Effort** S
**Where** `app/Services/CardTerminal/CardPaymentService.php:623-640` (`closeUnconfirmed`), `:188-195` (`capture`)

**What** The AI path has a deliberate rule (CLAUDE.md): a timeout or 5xx capture is "never resent… a second capture on one order could double it". It writes ahead (`inflight`) and flags `uncertain`. `closeUnconfirmed` ignores `mayHaveReachedTerminal`:
- On a read timeout or 5xx the intent stays `approved`, and a capture of `amount_cents` is sent again every 10 minutes, with no limit.
- The device capture path does the same: it rethrows and leaves the intent `approved`. The reconciler later captures the full hold, even if the device's smaller capture went through.

Either Payrallel double-charges, or every retry is refused and the intent never leaves `approved`. `closeUnconfirmed` is live today: it is the "device never confirmed" path.

**Evidence**
```php
} catch (CardTerminalException $e) {
    $intent->update(['last_error' => $this->errorText('auto-capture: '.$e->getMessage()),
        'last_queried_at' => Carbon::now()]);
    Log::error('Card auto-capture failed — retrying', ...);
    return $intent;   // same capture resent in 10 min, timeout or not
```

**Fix** Reuse the AI path's discipline. Write `inflight` before the call. On `mayHaveReachedTerminal`, mark the intent `uncertain` and hand it to `card-payments:resolve-ai-charge` (rename it to cover both paths). Alternatively, `query()` the provider before any re-capture.

**Verify** Add tests: a fake gateway throws a timeout `CardTerminalException` on capture, then the reconciler runs twice. Assert one capture call, and the intent is flagged rather than re-sent.

### CARD-03 — The T05 event log grows without limit, mostly from terminal-status polls
**Sev** Medium · **Lens** Performance · **Verdict** CONFIRMED (prod) · **Effort** S
**Where** `app/Services/CardTerminal/Payrallel/PayrallelGateway.php:149-154`, `CardTerminalEventLog::record`, `CardPaymentService::terminalStatus:247-283`

**What**

### CARD-04 — The per-intent cache lock (20 s) can expire inside one chain of provider calls; a lock wait gives the device a 500
**Status:** FIXED f2c6cf94d1 — lock = 3 × (timeout + connect) + 10 s (`CardPaymentService::lockSeconds()`); `LockTimeoutException` → 409.
**Sev** Medium · **Lens** Best practices / concurrency · **Verdict** PLAUSIBLE · **Effort** S
**Where** `CardPaymentService.php:36-38`, `:124-149` (`cancel`), `:841-845` (`locked`); `config/payrallel.php` timeout 8 s; `FreezerCardController::guard:174-183`

**What**
- `cancel()` can chain three calls: `cancelActiveRequest`, then `advance()` → `query`, then `voidNow` → `void`. At up to 8 s each that is about 24 s, past `LOCK_SECONDS = 20`. Another worker then gets the lock and acts on the same money.
- A duplicate void is harmless, but the class docblock claims "one provider call at a time per intent".
- `block(10)` throws `LockTimeoutException`, which `guard()` does not catch, so the device gets an HTTP 500 instead of 409 or 503.

**Evidence**
```php
private const LOCK_SECONDS = 20;
return Cache::lock('card-payment-intent:'.$intent->id, self::LOCK_SECONDS)
    ->block(self::LOCK_WAIT_SECONDS, fn () => $work($intent->fresh()));
```

**Fix** Set `LOCK_SECONDS` to at least 3 × (timeout + connect_timeout) + slack, or derive it from config. Catch `LockTimeoutException` in `guard()` and return a 409 the device can retry.

**Verify** Add a unit test with a gateway fake that sleeps, or assert the constant against the config.

### CARD-05 — Orphan `release()` checks and deletes without a row lock, so it can race a live TRADE adoption
**Status:** FIXED f2c6cf94d1 — locked re-read, conditional delete, Assign / Ignore in one transaction.
**Sev** Medium · **Lens** Correctness / concurrency · **Verdict** CONFIRMED (pattern), impact rare · **Effort** S
**Where** `app/Services/CardSettlement/CardSettlementOrphanSales.php:145-171`; callers `CardSettlementController::resolveRow:460`, `ignoreRow:493`, `CardSettlementUnsyncService::unsync:83`

**What**
- `release()` reads the orphan with `is_found_in_transaction = false` (no `lockForUpdate`), then deletes it by primary key unconditionally.
- `VendTransactionService::findSettlementOrphan` row-locks the same row while a late TRADE adopts it. The DELETE waits for that lock, then removes what is now the real adopted sale.
- In `resolveRow` and `ignoreRow` the release, the items delete, the sale delete and the row update are not in one transaction.

**Evidence**
```php
$sale = VendTransaction::withoutGlobalScopes()->whereKey(...)
    ->where('card_settlement_row_id', $row->id)->where('is_found_in_transaction', false)->first();
...
$sale->vendTransactionItems()->delete();
$sale->delete();
```

**Fix** Wrap the method in `DB::transaction`, use `->lockForUpdate()->first()`, and delete conditionally (`where('is_found_in_transaction', 0)->delete()`). Wrap `resolveRow` / `ignoreRow` in a transaction too.

**Verify** Add a test: an orphan adopted after `release()` reads it must survive.

### CARD-07 — An AI-judged capture above the hold has no upper bound
**Status:** OPEN — cap value awaits Brian (proposal: max(hold × 2, hold + S$10); above it capture the hold and record the rest owed).
**Sev** Medium · **Lens** Money risk (documented decision) · **Verdict** PLAUSIBLE · **Effort** S
**Where** `app/Services/CardTerminal/AiCaptureDecision.php:116-122`

**What** The single capture above the hold was Brian's decision on 2026-10-04 and is documented. There is no sanity cap, though: an AI miscount (for example 10 units taken on a 1-item cart) becomes a capture of 10× the cart, sent at once. The only guards are a single verified verdict and the cart matching the sale. The documented rule says nothing about a ceiling, so a cap would not contradict it.

**Evidence**

### SF-02 — Unauthenticated §7 SKU callback can clear barcodes or plant a wrong one (the AI verdict decides T05 charges)
**Sev** High · **Lens** Security / money · **Verdict** CONFIRMED · **Effort** S
**Where** `app/Http/Controllers/SmartFreezer/ZijiaSkuNotifyController.php:42-43,73-87`; `app/Services/SmartFreezer/Zijia/ZijiaSkuApprovalService.php:91-143,175-181`
**What** The documented `{pass, sku}` shape is accepted unsigned. `ZIJIA_SKU_CALLBACK_TOKEN` is unset (CLAUDE.md), so the token check is skipped and anyone who can reach `/api/smart-freezer/zijia/sku/notify` can send it.

$result = $this->approvals->applyApprovalCallback($payload);

1. Set `ZIJIA_SKU_CALLBACK_TOKEN` now (no application has been submitted with a token-less URL yet), and fail closed when it is empty.

**Verify** Invert the test at `:187`: with no token configured, an untokened rejection leaves the barcode unchanged. Add a test that an approval with a library barcode for an unrelated name does not write it.

### SF-03 — Banner ffmpeg transcoding runs in the HTTP request, on an ungated route

**Where** `app/Services/ApkMedia/BannerMediaNormalizer.php:110-150,245-246`; `app/Http/Controllers/ApkSettingController.php:524-553`; `routes/web.php:153-154`; `config/apk_media.php:24,33,37`

### HH-01 — The minute planner's cost grows with machines × slot history; `whereDate` defeats the index; nothing prunes the slot table
**Sev** Medium · **Lens** Performance · **Verdict** CONFIRMED (code + prod counts) · **Effort** M
**Where** `app/Services/HappyHour/HappyHourPlanner.php:172-176`, `:379-386`, `:501-504`; `app/Console/Kernel.php:104`
**What**
- **Per-machine queries every minute.** `planVend()` runs for every campaign × machine every minute. Each call loads today's slots (`$existing`) and runs `checkStartingSlot`, so at least 2 queries per machine per minute. Prod has 178 members on a 00:00–23:59 window, which is about 356 queries a minute before any ranking.
- **Index cannot be used.** `whereDate('slot_date', …)` compiles to `date(slot_date) = ?` (I checked `Grammar::dateBasedWhere`). That rules out the `(happy_hour_campaign_id, slot_date)` index for the date part. With the `vend_id` prefix, MySQL reads every slot the machine has ever had.
- **Close-out scan.** `closeEnded()` filters `units_sold IS NULL AND ends_at <= now`. Neither filter leads any index (the indexes are `(status, ends_at)` and `(vend_id, ends_at)`), so it scans the whole table every minute.
- **Growth.** Prod has 16,058 slots, 9,393 of them created in the last 24 h, so about 3.4M a year. There is no retention.
- **Blocks other commands.** `happy-hour:run` runs in the scheduler's foreground (no `runInBackground`), so a slow run delays the every-minute commands listed after it. One example is `ops:freeze-stock-in`.

**Evidence**
```php
$existing = HappyHourSlot::query()
    ->where('happy_hour_campaign_id', $campaign->id)
    ->where('vend_id', $vend->id)
    ->whereDate('slot_date', $now->toDateString())   // date(`slot_date`) = ?
    ->get();
...
$slots = HappyHourSlot::query()->whereNull('units_sold')->where('ends_at', '<=', $now)->get();
```
**Fix**
- Load today's slots once per campaign, `->where('slot_date', $today)` (a plain `where`), then `groupBy('vend_id')` and pass each group to `planVend`. Do the same for the starting-slot check.
- Add an index `(happy_hour_campaign_id, slot_date, vend_id)`.
- For `closeEnded`, add an index `(units_sold, ends_at)` and bound the window (`ends_at > now − 2 days`).
- Add a `happy-hour:prune` command, or archive slots older than N months that no sale references.
- Add `->runInBackground()` to the schedule entry.

**Verify** Count queries in one `happy-hour:run` with 178 bound machines (`DB::listen`). Target: O(campaigns) queries, not O(machines). Also run `EXPLAIN` on the new `$existing` query.

### HH-02 — Slot totals are computed for every slot and never read; the "re-open" reset can be lost
**Sev** Medium · **Lens** Performance / Design · **Verdict** CONFIRMED · **Effort** S–M
**Where** `HappyHourPlanner.php:499-517`; `app/Services/HappyHour/HappyHourSales.php:68-123`, `:503-507`
**What**
- **Unused writes.** `closeEnded()` runs `results()` for every finished slot: a `vends` lookup plus a single-sale query plus a basket query. That is about 3 queries × 9.4k slots/day ≈ 28k queries a day. It writes `units_sold`, `revenue_cents` and `discount_cents`. Nothing reads them: the only other use of `units_sold` is as a "closed" flag. The page and the graph recompute everything from `vend_transactions` (see HH-03). CLAUDE.md says the same: "a closed slot's `units_sold` is not used".
- **Lost-update race.** `write()` decides whether to reset `units_sold` from the slot rows it read *before* its transaction. This can happen:
  1. `tag()` reads the slot while `units_sold` is still null.
  2. `closeEnded` computes and writes the totals.
  3. `tag()` commits the new tag but skips the reset, because its in-memory copy said null.

  The late sale is then never counted. Timing makes this likely: slots end on the minute and the planner runs on the minute, which is when late TRADEs inside the grace period arrive.

**Evidence**
```php
// HappyHourSales::write — decision taken from rows read before the transaction
$closed = $slots->whereIn('id', array_keys($tagged))->whereNotNull('units_sold')->pluck('id')->all();
if ($closed !== []) {
    HappyHourSlot::whereIn('id', $closed)->update(['units_sold' => null]);
}
```
**Fix**
- Option 1: make `HappyHourCampaignStats` and `slotTotals` read the stored slot columns for closed slots, and compute live only for open slots. That uses the work already being paid for and removes most of HH-03.
- Option 2: stop computing them and drop the columns.
- Either way, do the reset in the database inside the transaction: `HappyHourSlot::whereIn('id', array_keys($tagged))->whereNotNull('units_sold')->update(['units_sold' => null])`.

**Verify** Write a test that tags a sale between `results()` and `update()` (a mocked `HappyHourSales` that commits a tag inside `results`), then assert the next run recounts it.

### HH-03 — Campaign page figures scan every sale of every member machine, per window, per campaign, on every page view
**Sev** Medium · **Lens** Performance · **Verdict** CONFIRMED (prod: 43,382 rows read for 216 tagged) · **Effort** M
**Where** `app/Http/Controllers/HappyHourCampaignController.php:71`, `:86-89`; `HappyHourSales.php:157-221`; `app/Services/HappyHour/HappyHourCampaignStats.php:104-109`
**What**
- **One page view.** `index()` calls `slotTotals` once, then `window()` twice per campaign (last 24 h and last 30 days). Each call runs two `dailyTotals` queries: `vend_id IN (≈178) AND transaction_datetime BETWEEN … AND happy_hour_slot_id IS NOT NULL`.
- **No index on the filter.** `happy_hour_slot_id` has no index, so every sale row in the range is fetched. On prod that is 43,382 sales over 30 days for campaign 4's machines, of which 216 are tagged (0.5%).
- **Duplicated work.** The 30-day window already contains the 24-hour one, and both are recomputed on every load.
- **Grows linearly.** The cost scales with the number of campaigns, including paused ones, and with fleet sales.
- **About the "no index" decision.** CLAUDE.md's "No index … on purpose" is right for reading one slot through `(vend_id, transaction_datetime)`. It is wrong for fleet-wide 30-day totals.

**Evidence**
```php
->whereIn('t.vend_id', $vendIds)
->whereBetween('t.transaction_datetime', [$from, $to])
->whereNotNull('t.happy_hour_slot_id')    // unindexed; 0.5% selectivity
```
**Fix**
- Preferred: use the HH-02 stored totals for closed slots.
- Or start from `happy_hour_slots` (the campaign's slots in range, a small set) and join to `vend_transactions` on `happy_hour_slot_id`. That needs an online `INPLACE` index on `vend_transactions(happy_hour_slot_id)`, which is fine on MySQL 8.
- Also compute the last-24 h figures from the 30-day rows in PHP, and cache the page figures for about 60 s.

**Verify** Count queries and rows examined for `GET /happy-hour-campaigns` before and after (Telescope or the slow log).

### HH-04 — A campaign save and the minute run plan the same machines with no lock; the run can write slots from settings that were just replaced
**Sev** Medium · **Lens** Best practices (correctness, race) · **Verdict** PLAUSIBLE (code path traced, not reproduced) · **Effort** M
**Where** `HappyHourCampaignController.php:128-142`; `HappyHourPlanner.php:55-70`, `:112-123`
**What**
- **The race.** `run()` loads all active campaigns once at the start, then plans about 178 machines one by one, which takes seconds when rankings are due. `update()` runs `cancel()` inside a transaction, commits, then runs `planCampaign()` in the HTTP request. `withoutOverlapping` only stops the command overlapping itself.
- **How it goes wrong.** If the run reaches a machine after the save's cancel commits but before `planCampaign` plans that machine, the run creates a slot from the *old* snapshot: old discount, rounding and exclusions. `planCampaign` then finds the time covered and skips it, so the old price runs for the whole slot (60 min).
- **Two concurrent planners.** Two planners picking *different* SKUs for the same time can also exceed `skus_per_slot`. The unique key `(vend_id, starts_at, product_id)` only catches the same SKU.
- **Planning in the request.** A schedule edit on the group campaign re-ranks all 178 machines inside the HTTP request (about 8 queries each).

**Evidence**
```php
DB::transaction(function () use ($request, $campaign, $now) {
    ...
    if ($reschedule) { $this->planner->cancel($campaign, $now); }
});
$this->followGroups();
$this->planNow($campaign->fresh());   // races the minute run's stale $campaigns
```
**Fix**
- Hold one `Cache::lock('happy-hour:planner', 120)` around `HappyHourPlanner::run()`, and around the controller's cancel → followGroups → planCampaign sequence (`block(30)`).
- Better: have save dispatch a `ShouldBeUnique` queued `PlanHappyHourCampaign` job that takes the same lock.
- Inside `planVend`, re-read `updated_at` and skip the machine if the campaign changed since the run started.

**Verify** A feature test that saves a new `discount_pct` between `run()` loading campaigns and `planVend` (via a ranker double), then asserts that no slot carries the old price.

### Done well
- **Money arithmetic.** `HappyHourPricing::promoPrice` works in hundredths of a cent, rounds up to the step, and falls back to rounding down so a discount always remains. It is integer-only and tested at the boundaries.

- **Safe tagging.** Tagging runs once, after commit, and never throws on the MQTT ingest path. Vending `HH` entries are bounds-checked (`positiveInt`, at most 50 entries, slot must belong to the same machine and product, time inside the slot plus grace).
- **Basket reprice.** It rewrites only when the result provably adds up to the header amount. One `planVendingBasketReprice` decision is shared by the live path and the repair command, and the command defaults to a dry run.
- **Planner robustness.** Ranking is lazy, at most once per machine per run (`eligibleOnce`). Each machine runs in its own `try/catch`. Slot creation is idempotent (unique key plus catching `UniqueConstraintViolationException`). Nudges are debounced (`Cache::add`) and dispatched `afterCommit`.
- **Operator isolation.** It is a global scope, with explicit `withoutGlobalScope` only where every campaign must be judged. A save never unbinds machines the viewer cannot see. All of this has regression tests.
- **Tests.** The 58 feature tests assert observable behaviour (rotation order, priority positions, sold-out refill, tag rules, refund promo price), not just "returns 200".

### Checked and OK

- **Mass assignment.** `safe()->except('vend_ids')` plus `$fillable`; `operator_id` and `created_by` are never taken from the request.
- **Validation.** Ranges and enums are checked. `skus_per_slot lte sku_count`. A SKU cannot be both prioritized and excluded.
- **Every-minute paths.** `endSoldOut` reads stock in one grouped query; `HappyHourPause` makes 2 queries per call regardless of machine count; `HappyHourEligibility` makes no queries.
- **Scheduling.** `withoutOverlapping(5)`: the lock expires quickly, so a killed run cannot block the planner for 24 h.
- **Migrations.** All are reversible. The `happy_hour_slot_id` add is an instant column add. The only edit to an already-pushed migration (`2026_10_11`, `c934f9272f`) changed a comment only.
- **Front-end safety.** Tooltip HTML is escaped (`escapeHtml`), and floating-vue's default `html: false` covers plain-string tooltips. The stats loader guards against out-of-order responses (ticket counter).
- **Data volume.** `syncActive` reloads about 460 active vends (≈60 KB of `apk_ver_json`) every minute. That is acceptable today.

### CORE-03 — Freezer stock: queued `SyncVendChannels` can write an old qty back over a sale
**Sev** Medium · **Lens** Correctness (stock) · **Verdict** CONFIRMED (code path; happens only rarely) · **Effort** S
**Where** `app/Services/Freezer/FreezerChannelSync.php:67`; `app/Jobs/Vend/SyncVendChannels.php:57,111,168`

### UI-06 — Setting/Edit: three watchers on `form.product_mapping_id` with a module-level revert flag
