### [M1-01] Gateway webhook is unauthenticated and unverified for Omise/Midtrans
- **Severity:** High
- **Category:** practice
- **Status:** FIXED 612e033478 — `enforce` ON in prod since 2026-09-15 22:09 (env `PAYMENT_WEBHOOK_VERIFICATION=enforce`); 114/114 log-mode + first 5 inline verdicts verified, 0 refused, approvals dispensing
- **Where:** `app/Http/Controllers/PaymentController.php:52-312`, `routes/api.php:35`, `app/Http/Kernel.php:44-48`
- **What:** `POST /api/v1/payment-gateway-status/{company}` sits in the unauthenticated v1 group (only `throttle:api`). Only the `fiuu` branch verifies a signature (`Fiuu::verifyResponse`, line 214). For `omise`/`midtrans` the body is trusted as-is: `data.status = successful` + a `metadata.order_id` of any PENDING log flips it to APPROVE, dispatches `CreateGatewayVendTransaction` and `processPayment()` → a dispense frame to the machine; `data.object = refund` on an APPROVE log runs `OmiseRefundRecorder::record` (sets `is_refunded`, `SETTLEMENT_REFUNDED`, crosses tickets). Omise does not sign events — the documented pattern is to re-fetch the event/charge from the API by id before acting.
- **Evidence:** No `verify`/`signature`/`X-Omise` anywhere in `app/` except Fiuu (grep). Order ids are guessable (`RunningNumberService::getVendOrderID` = `ymdHis` + 5-digit vend code) and a PENDING log exists the moment a QR is requested at the machine.
- **Impact:** Free product on any QR machine (forge approve after requesting a QR), and forged "refunded" marks that hide real charges from the refund surfaces and pull approved tickets to Rejected (`markAutoRefundedByCharge`).
- **Fix:** For Omise, on `charge`/`refund` events call `GET /events/{id}` (or `GET /charges/{id}` / `GET /refunds`) with the operator's secret key and act only on the fetched object; for Midtrans verify `signature_key` (sha512 of order_id+status_code+gross_amount+server_key). Reject anything unverifiable with 400 and log it. Optionally add an IP allowlist middleware for the route as defence in depth.
- **Verify:** `tests/Feature/PaymentWebhookAuthenticityTest.php`: a forged successful-charge body against a PENDING log must leave status=1 and dispatch nothing; a fetched-and-matching event still approves.
- **Effort:** M

### [M1-02] Product-level sales aggregators ignore the settlement gate — refunded/pending gateway rows count as product sales

- **Category:** logic
- **Status:** FIXED b93bc2c1d8 + 40266b5999 (rebuild now deletes stale groups) - deployed 2026-09-16, vpr:rebuild 2026-08-01..09-15 run twice (0 failures); every day 09-02..09-15 now equals a gated recompute to the cent

### [M1-03] Orphan adoption compares a float-truncated amount for `transf_info` card TRADEs
- **Severity:** Medium
- **Category:** logic
- **Status:** FIXED 9335f1351f - deployed 2026-09-16 16:46 + subscriber restarted, prod-validated (0 swallowed errors, duplicates now info-level, ingest rate unchanged)
- **Where:** `app/Services/VendTransactionService.php:1038` (`$input['Price'] * 100`), `:610` (`->where('amount', (int) $input['amount'])`), `:129`
- **What:** For frames carrying `transf_info` (every APK-built card TRADE — prod shows `Price` "4.6", "2.9", "3.3"…), `amount` becomes a float (`4.6*100 = 459.99999999999994`). MySQL rounds it to 460 on INSERT, but `findSettlementOrphan()` casts with `(int)` → 459, so a late card TRADE for $4.60 / $2.30 / $1.15 / $5.10 / $4.35 / $8.20 never finds the NETS orphan created for it and inserts a second row.
- **Evidence:** `php -r` check: 4.6→459, 2.3→229, 1.15→114, 5.1→509, 4.35→434, 8.2→819 (3.3/2.9/4.7 are exact). Prod: 1,029 $4.60 card sales in 6 days. Adoption only fires when the report was synced before the TRADE arrived (>1 day late), so the duplicate rate is low but every hit double-counts revenue until `orphans-audit`.
- **Impact:** Duplicate settled sales (orphan + real) on a subset of prices; the reconciler then marks the real sale `not_captured` and can tick a failed one "NA in NETS" wrongly.
- **Fix:** Normalise once in `processInput`: `$data['amount'] = isset($input['Price']) ? (isset($input['transf_info']) ? (int) round($input['Price'] * 100) : (int) $input['Price']) : 0;` (reuse `normalizeAmountToCents`). Then `(int)` casts downstream are safe.
- **Verify:** Unit test: `transf_info` frame with `Price = "4.6"` adopts an orphan with `amount = 460`. Prod: `SELECT COUNT(*) FROM vend_transactions WHERE card_settlement_row_id IS NOT NULL AND is_found_in_transaction=0 AND amount IN (460,230,115,510,435,820)` before/after.
- **Effort:** S

### [M1-04] TRADE ingest swallows every exception, defeating the job's "fail loudly" backstop
- **Severity:** Medium
- **Category:** logic
- **Status:** FIXED 9335f1351f - deployed 2026-09-16 16:46 + subscriber restarted, prod-validated (0 swallowed errors, duplicates now info-level, ingest rate unchanged)
- **Where:** `app/Services/VendTransactionService.php:264-268`; `app/Jobs/Vend/CreateVendTransaction.php:60-73`
- **What:** `create()` wraps the whole `DB::transaction` in `catch (\Exception $e) { Log::error(...); return; }`. `QueryException` extends `Exception`, so the job's `isDuplicateEntry` branch and its "anything that is not a duplicate-key violation still fails loudly" contract never execute: FK/NOT NULL violations, lock-wait timeouts (1205 after the 3 deadlock retries), and any runtime error in `applyTradeToPreCreatedRow` are logged at error level and the job completes successfully. The machine already received its ack from `VendDataService` (the job is queued), so the sale is gone.
- **Evidence:** Job docblock line 63-66 vs service line 264. Horizon `tries=1`, so there is no retry either way.
- **Impact:** Silent sale loss with no `failed_jobs` row, no dirty-day mark, no counter. Only the log line remains.
- **Fix:** Narrow the catch: rethrow anything that is not a duplicate-entry `QueryException` (`errorInfo[1] ∈ {1062,1586}`), let the job decide; keep the log. Give `CreateVendTransaction` `$tries = 3` with backoff for 1205/1213 only.
- **Verify:** Feature test forcing a NOT NULL violation (e.g. `vend_channel_id` null) must surface as a failed job; grep prod log for `Error creating vend transaction` to size the current loss.
- **Effort:** S

### [M1-07] `SET innodb_lock_wait_timeout = 5` leaks onto the queue worker's connection for every later job
- **Severity:** Medium
- **Category:** performance
- **Status:** FIXED 9335f1351f - deployed 2026-09-16 16:46 + subscriber restarted, prod-validated (0 swallowed errors, duplicates now info-level, ingest rate unchanged)
- **Where:** `app/Services/VendTransactionService.php:87-90`
- **What:** `innodb_lock_wait_timeout` is a session variable; Horizon workers keep one PDO connection across jobs, so after the first TRADE on a worker every subsequent job on that connection — `StoreVendsRecord` upserts, `GpMetricsAggregator::persistDay` (delete + bulk insert of ~50k rows), `CardSettlementSyncService` chunked UPDATEs, `MissingTradeMarker` FOR UPDATE chunks — runs with a 5 s lock timeout instead of the server default. `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` only applies to the next transaction, so attempts 2-3 of the retry loop run REPEATABLE READ.
- **Evidence:** `supervisor-1` handles `['high','default']` where both `CreateVendTransaction` and the rollup chains are dispatched (`Kernel.php:124`, `RollupRebuilder::DEFAULT_QUEUE = low` for some but `store:previous-day-vend-records` dispatches to default). `GpMetricsAggregator::isDeadlock` already retries 1205, which suggests the timeouts are being hit.
- **Impact:** Spurious lock-wait failures on heavy jobs sharing a worker; inconsistent isolation across retries.
- **Fix:** Replace with a transaction-scoped statement: run `SET innodb_lock_wait_timeout` only inside the closure and reset in `finally`, or drop it and rely on `DB::transaction(..., 3)`; move the isolation SET inside the closure so every attempt gets it.
- **Verify:** `SELECT @@session.innodb_lock_wait_timeout` from a job dispatched after a TRADE on the same worker (debug only); watch for 1205 in `gp_metrics` retry warnings after the change.
- **Effort:** S

### [M1-08] Item rows of a multi gateway sale are deleted and recreated on TRADE, orphaning refund ticket item links

- **Status:** CONFIRMED (code); frequency PLAUSIBLE

### [M3-07] The MQTT "1" ack is a queued, fire-and-forget job on the shared `default` queue — the fleet's 6/10-minute self-reboot timer is coupled to queue depth and Redis durability
- **Severity:** Medium
- **Category:** logic
- **Status:** CONFIRMED
- **Where:** `app/Services/VendDataService.php:495-500`, `app/Jobs/PublishMqtt.php:14-15`, `config/horizon.php:171-178`
- **What:** Every heartbeat/TRADE ack is `PublishMqtt::dispatch('CM'.$code, $response, 0)->onQueue('default')` with `$timeout = 5; $tries = 1`. `default` is the same queue as `CreateVendTransaction`, `SyncVendParameter`, `SyncVendTransactionTotalsJson`, `SendOperatorCallback`, etc. The APK reboots after 360 s (big) / 600 s (small) without an ack (`FREEZER_TELEMETRY_SPEC.md §2`).
